# technical research: Vercel + Nx + NestJS + TypeORM/Neon production deployment

**Decision this research serves:** De-risk Story 4.1 ("Deploy to Vercel + Neon") before implementation starts — confirm the current (2026) Vercel/Nx/NestJS deployment mechanics, verify the architecture doc's "Native NestJS support confirmed 2026-07-06" claim, and resolve the specific TypeORM-vs-PgBouncer-transaction-pooling risk already flagged in architecture review.

## Executive Summary

**All five areas resolve favorably for this stack, with one real nuance (Nx's Root Directory guidance) and one important config addition (migration URL vs. runtime URL) that Story 4.1 needs to get right on the first attempt.**

1. **Two Vercel Projects, one repo** is the correct and only supported mechanic for `apps/web` + `apps/api` — confirmed directly from Vercel's current docs [1]. The one wrinkle: Vercel's generic monorepo docs say to set each Project's Root Directory to the app subfolder [1], but Nx's own docs recommend the opposite — leave Root Directory at the repo root and override the Build Command / Output Directory instead, because Nx needs the whole workspace graph present in the build container [3]. **Follow Nx's guidance, not the generic monorepo flow**, for both `apps/web` and `apps/api`.
2. **The architecture doc's "Native NestJS support confirmed 2026-07-06" claim is still accurate as of this research pass** (2026-08-25) — Vercel's NestJS docs page itself carries a `last_updated: 2026-07-06` stamp [6], so this is very likely the exact page the earlier research checked. It's genuinely zero-config for a *conventional* NestJS repo: no adapter, no `serverless-http`-style wrapper, just a standard `NestFactory.create(AppModule)` + `app.listen()` bootstrap, deployed as a single Vercel Function running on Fluid compute [6]. **The one gap**: Vercel's docs don't address the Nx-monorepo case for NestJS specifically the way they do for Next.js. Given Nx's explicit instruction to override Build Command/Output Directory for Next.js on Vercel [3], the same override is almost certainly needed for `apps/api` too — this is a reasoned inference, not a directly documented fact, and should be the first thing verified empirically in Story 4.1 (deploy a trivial `apps/api` first, confirm the entrypoint is actually found).
3. **The TypeORM/PgBouncer risk is real in general but does not apply to this stack's default configuration.** TypeORM's `postgres` driver runs on `pg` (node-postgres), and `pg` only creates a *named* (session-persistent) prepared statement when the caller explicitly supplies a `name` in the query config [13]. TypeORM's query runner does not do this for ordinary parameterized queries — it sends unnamed Parse/Bind/Execute, which completes in one round trip and never needs to survive across a PgBouncer transaction boundary. This is precisely why Prisma has years of open GitHub issues about PgBouncer + prepared statements [16] (it *does* cache named statements by default and needs an explicit opt-out) while a targeted search of `typeorm/typeorm`'s issue tracker for "pgbouncer" turns up zero reports about prepared statements [17]. **No statement-cache-disabling flag, and no switch to `@neondatabase/serverless`, is needed for TypeORM's runtime queries.** The one place this changes: migrations. Neon's own official TypeORM guide is explicit that the pooled string is for the running app, and a **direct** (non-`-pooler`) connection string must be used for running TypeORM migrations, because migration tooling relies on session-scoped behavior transaction pooling doesn't support [11].
4. **Env vars are scoped per Vercel Project, not per repo** — `apps/web` and `apps/api` each need `DATABASE_URL` (and anything else) set independently in their own Project settings [1][4]. Two Nx-specific traps to avoid: Nx's build cache can silently replay a stale env var value unless that var is declared as a cache input in `nx.json` [4]; and hardcoding a CORS origin on `apps/api` will break every Preview deployment of `apps/web`, since Preview URLs are unique per deployment [19].
5. **Everything else** (autosuspend cold starts, bundle size limits, migration-vs-runtime connection strings, double connection-pooling) has concrete, citable mitigations below — none are blockers, all are one-line config decisions Story 4.1 should make deliberately rather than discover at deploy time.

## Findings

### 1. Deploying an Nx monorepo with two apps to Vercel

**Mechanic confirmed: one Vercel Project per app, same Git repository.** Vercel's own monorepo docs describe the exact flow: click "Add New… → Project," repeat for each directory you want to deploy, and set each Project's Root Directory to the relevant app folder — "This will configure the root directory of each project to its relevant directory in the repository" [1]. Every push then triggers a parallel deployment for each connected Project, and both show up as separate deployment checks/comments on the PR [1]. The number of Vercel Projects you can connect to one repo is plan-limited but not capped at one [1].

**The Nx-specific wrinkle.** Vercel's Nx-specific doc says the platform "handles all aspects of configuring your monorepo, including build commands, the Root Directory... and the correct directory for npm workspaces" when you import through the Nx-aware flow, provided you're on `nx` v17+ [2]. But Nx's own docs for deploying a Next.js app from an Nx workspace to Vercel are more prescriptive and, notably, contradict the generic "set Root Directory to the app subfolder" instructions: *"If you are importing your Nx workspace's repository for the first time, make sure you leave the Root Directory field empty. Do not set it to `./` or any subdirectory. Vercel will use the full repository root, which is required for Nx to work correctly."* Then: expand "Build and Output Settings," override the Build Command to `npx nx build <app-name>`, and override the Output Directory to point at the built app's output (e.g., the `.next` folder for a Next.js app) [3]. The likely reconciliation: Vercel's "Nx-aware" import flow (framework preset = Nx) is doing exactly this automatically under the hood — root-at-repo, build/output inferred per selected project — while the generic monorepo docs describe the older, framework-agnostic flow that predates Nx auto-detection. **Recommendation: follow Nx's explicit guidance for both Vercel Projects** (root directory = repo root; override Build Command and Output Directory per project) rather than assuming the generic "Root Directory = subfolder" flow will correctly wire up Nx's dependency graph.

**Avoiding redundant builds.** Two options, not mutually exclusive:
- **"Skip unaffected projects"** — Vercel's built-in, zero-config mechanism: a project is considered unchanged (and its build skipped, without consuming a concurrent-build slot) if neither its source, its internal dependencies, nor a lockfile change affecting only its own deps, changed in the commit. Requires npm/yarn/pnpm/Bun workspaces with unique `name` fields and explicit inter-package dependencies in `package.json` [4].
- **`nx-ignore` in "Ignored Build Step."** The `npx nx-ignore <project-name>` script (from `nrwl/nx-labs`) uses Nx's affected-graph to decide whether to cancel the build; wire it into each Project's Settings → Git → Ignored Build Step field [4]. Caveat: this has real, currently-open breakage reports against recent Nx/Vercel build-image combinations (`nrwl/nx#20320` — "Cannot find installed Nx"; `nrwl/nx#10642` — doesn't trigger correctly) [5]. Given this project has exactly two apps, **prefer "Skip unaffected projects" first** — it's built-in, doesn't need a workspace script, and has no open breakage reports — and only reach for `nx-ignore` if the workspace-detection requirements aren't met.

**Remote caching** (not required for a 2-app project, noted for completeness): Nx 20+ deprecated the old custom task-runner-based `@vercel/remote-nx` package in favor of an HTTP-based self-hosted cache API; there's no first-party Vercel-hosted Nx remote cache equivalent to Turborepo's anymore as of Nx 20+ [2].

### 2. Vercel's native NestJS support — verification and detail

**Verified, and current.** Vercel's NestJS docs page is unambiguous: *"You can deploy a NestJS app to Vercel with zero configuration using Vercel Functions"* [6]. This is a real, no-adapter, no-wrapper path — the entire app is a single Vercel Function:

```ts
// src/app.ts or src/main.ts (one of a fixed set of recognized entrypoint filenames)
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
bootstrap();
```

No `serverless-http`, no `@vendia/serverless-express`, no manual `createServer`/handler export — Vercel's build step inspects the app for one of these recognized entrypoint files and wraps it itself: `src/main.{js,mjs,cjs,ts,cts,mts}`, `src/app.*`, `src/index.*`, `src/server.*`, or the same four names at the repo/app root [6].

**This page's own metadata (`last_updated: 2026-07-06`) matches the architecture doc's citation date almost exactly**, strongly suggesting this is the exact source the 2026-07-06 check already found — so the architecture doc's claim is corroborated, not just repeated.

**What changed / what to know beyond "yes it's native":**
- The app runs on **Fluid compute by default** — pay-for-CPU-used pricing, automatic cold-start reduction, and importantly, **concurrent requests can be served by the same warm instance** [6]. This means any accidentally-module-scoped mutable state in the NestJS app (e.g., an in-memory counter) would leak across concurrent users. This project's own architecture already avoids the one place this would bite — rate-limit state is Postgres-backed per AD-2, not in-memory — so this is a validating cross-check, not a new requirement, but worth an explicit sanity pass before go-live.
- **Minimum Vercel CLI version 48.4.0** is required for both `vercel dev` (local dev against the same code path as production) and `vc deploy` on this NestJS path [6].
- **Standard Vercel Functions limits apply**: 250MB bundle size by default, up to 5GB via the "Large Functions" beta on Fluid compute [6][8]. LangChain.js's dependency tree is worth auditing against this before assuming it's a non-issue.
- **Duration limits**: Hobby plan functions can run up to 60s (new projects; legacy default is 10s); Pro/Enterprise with Fluid compute get up to 800s by default, with a 1800s extended-duration beta requiring function-level `maxDuration` config [8].
- **Cron and SSE are supported** but need explicit `vercel.json`/decorator wiring (`crons` array; `@Sse()` decorator + RxJS `Observable`) — not relevant to this story's AC but useful to know the platform doesn't silently support long-lived connections without configuration [7].

**Open/unverified point (flagged, not asserted as fact):** none of Vercel's NestJS or Nx documentation explicitly describes the combination — a NestJS app built by an Nx executor (webpack/esbuild via `@nx/webpack` or `@nx/esbuild`, output to something like `dist/apps/api/main.js`) rather than the conventional `nest build` (`dist/main.js`). Given Nx's explicit instruction to override Build Command and Output Directory for the Next.js case rather than trust framework auto-detection [3], the safe assumption is that `apps/api` will need the same override (`npx nx build api` + an explicit Output Directory pointing at Nx's actual dist path) rather than relying on Vercel's "zero-config" NestJS entrypoint scan, which is written with a conventional non-monorepo repo layout in mind. **Recommend Story 4.1 verify this empirically as step one** (deploy a trivial `apps/api` build before wiring up the real app) rather than assume zero-config "just works" through Nx.

### 3. TypeORM vs. Neon's PgBouncer transaction-pooling endpoint — the core risk

**Mechanism, confirmed from Neon's own docs.** Neon's pooled connection string (hostname with `-pooler` appended to the endpoint ID) runs through PgBouncer in transaction pooling mode, which returns the backend connection to the pool after each transaction completes. This mode explicitly does **not** support: `SET`/`RESET`, `LISTEN`/`NOTIFY`, SQL-level `PREPARE`/`DEALLOCATE`, `WITH HOLD` cursors, or temp tables with `PRESERVE`/`DELETE ROWS` semantics [9]. This is exactly the class of risk the architecture review flagged.

**The critical distinction PgBouncer draws: SQL-level vs. protocol-level prepared statements.** SQL-level `PREPARE ... EXECUTE` genuinely does not work under transaction pooling — a prepared statement lives on one specific backend Postgres process, and transaction pooling gives no guarantee a client reconnects to that same backend for its next transaction [10][14]. But **protocol-level** prepared statements (the wire-protocol Parse/Bind/Execute mechanism used by client-driver libraries, not raw SQL text) are explicitly supported and recommended by Neon: *"Protocol-level prepared statements ARE supported... check your driver's documentation for details"* [9]. PgBouncer itself gained first-class support for this in version 1.21 via a `max_prepared_statements` setting that lets it transparently re-prepare a statement on whichever backend connection is actually in use, per-name, per-connection [10][14] (the DEALLOCATE side of this has a known gap — client-issued `DEALLOCATE` at the protocol level isn't supported yet, pending upstream Postgres protocol support [14] — not relevant to TypeORM, which doesn't issue explicit `DEALLOCATE`).

**Why this doesn't bite TypeORM by default.** node-postgres (`pg`, the actual driver underneath TypeORM's `type: 'postgres'`) only creates a **named** prepared statement — the kind whose lifetime needs to persist across queries/transactions on a specific backend connection, i.e. the kind PgBouncer transaction pooling breaks — if you explicitly supply a `name` field on the query config object: *"If you supply a `name` parameter the query execution plan will be cached on the PostgreSQL server on a per connection basis"* [13]. TypeORM's Postgres query runner does not pass a `name` for its ordinary parameterized queries; it relies on `pg`'s default behavior, which is an **unnamed** statement — parsed, bound, and executed in a single round trip that completes within one transaction and creates no server-side state that needs to survive to the next query. This is safe under transaction pooling by construction: Parse+Bind+Execute for an unnamed statement never spans a transaction boundary the way a *reused* named statement would.

This isn't a theoretical distinction — it's exactly what separates TypeORM's experience from Prisma's here. Prisma's query engine caches named prepared statements client-side by default and needs an explicit `?pgbouncer=true` connection-string flag (or, on newer PgBouncer, careful `max_prepared_statements` tuning) to avoid `prepared statement "sN" already exists` / `does not exist` errors — this has been an open, recurring GitHub issue thread for Prisma for years [16]. By contrast, a targeted search of TypeORM's own issue tracker (`repo:typeorm/typeorm pgbouncer`) returns exactly 3 results, none of them about prepared statements (they're about connection release/reconnect edge cases unrelated to pooling mode) [17]. The absence of a multi-year "TypeORM + PgBouncer + prepared statements" saga, in an ecosystem where the Prisma equivalent is extremely well documented, is itself corroborating evidence that TypeORM's default query path doesn't trigger this class of bug.

**Conclusion: no TypeORM configuration change (no `extra.statement_cache_size`-style flag, no disabling of anything) is needed for ordinary application queries against Neon's pooled endpoint.** TypeORM's `extra` object passes straight through to `pg.Pool`'s constructor options if any tuning is ever needed [15], but nothing in `pg`'s or TypeORM's default configuration needs changing for this specific risk.

**What *does* need explicit handling: migrations, not queries.** Neon's own official TypeORM connection guide states this directly: *"Use a pooled connection string for your application at runtime, but use a direct (non-pooled) connection string when running TypeORM migrations"* — because migration tooling relies on session-level behavior (potentially `SET`s, advisory locks, or multi-statement DDL sessions) that transaction pooling doesn't support [11]. Practically, this means **two separate connection-string env vars**: `DATABASE_URL` (pooled, `-pooler` hostname) consumed by the running `apps/api`, and a second direct (`-pooler`-less) URL used only by whatever process runs TypeORM migrations. Per this project's AD-10/AD-11, the *ingestion* script performs data writes inside a single per-paper transaction (not DDL) — that pattern is exactly what transaction pooling is designed to support natively (one client transaction = one backend connection, held for its duration), so **ingestion can safely run against the pooled connection**; it's specifically schema migrations (and `synchronize: true`, if ever considered — which also issues DDL — should never be used against the pooled endpoint) that need the direct string.

**Should this project use `@neondatabase/serverless` instead of `pg`, for TypeORM specifically?** No — and this has a clear, sourced rationale. `@neondatabase/serverless` is a driver with an API surface that mirrors node-postgres's `Pool`/`Client`, but it replaces the TCP wire protocol with HTTP or WebSocket transport, purpose-built for runtimes that don't support raw TCP sockets — edge functions, Cloudflare Workers, etc. [Q2 research; general knowledge of the driver confirmed via search]. Since this project deploys `apps/api` as a standard Vercel Function (Node.js runtime, Fluid compute) rather than an Edge Function, full TCP connectivity to Neon is already available — there is no environmental constraint forcing a transport-layer swap. Additionally, TypeORM has no first-class "driver adapter" mechanism the way Prisma (`@prisma/adapter-neon`) or Drizzle (`neon-http`/`neon-serverless` dialects) do [search findings]; swapping TypeORM's underlying driver for `@neondatabase/serverless` would mean unsupported module-resolution tricks, not a documented, maintained integration path. **Recommendation: keep `type: 'postgres'` (i.e., `pg`) and Neon's pooled connection string; do not adopt `@neondatabase/serverless`.**

**Related, concrete config to set:** Neon's compute auto-suspends after 5 minutes of inactivity on the free tier, and reactivating it adds "a few hundred milliseconds" of cold-start latency on top of normal connection time [12]. Neon's docs recommend a generous connection timeout to absorb this — `connectionTimeoutMillis: 10000` for Node.js clients generally [12], or equivalently `connect_timeout=10` appended to the connection-string URL, which is the form Neon's own TypeORM guide shows directly in the `DATABASE_URL` value [11]. For TypeORM specifically, since the DataSource is configured with `url: process.env.DATABASE_URL`, the query-string form (`...&connect_timeout=10`) is simplest — `pg`'s connection-string parser understands this libpq-style parameter directly.

**One more sizing note:** TypeORM's own internal `pg.Pool` (sized via `extra.max`, defaulting to `pg`'s own default of 10) sits *on top of* Neon's PgBouncer pool. Every concurrent warm Vercel Fluid-compute instance running `apps/api` will hold its own small pool against the shared PgBouncer pool behind it — exactly the "many small pools stacked in front of one shared pool" pattern PgBouncer/the pooled endpoint exists to absorb, so this isn't a new risk, but it's worth deliberately setting `extra.max` to a modest number (e.g., low single digits) per DataSource rather than leaving it at whatever `pg`'s default happens to be, since AD-1/AD-3's entire rationale is protecting Postgres's real connection ceiling under serverless fan-out.

### 4. Environment variables / secrets across two Vercel Projects sharing a repo

**Env vars are scoped per Project, not per repository.** Each of the two Vercel Projects (`apps/web`, `apps/api`) has its own independent environment variable configuration; nothing defined in one is automatically visible to the other, even though both track the same Git repo [1]. `DATABASE_URL` needs to be set explicitly on `apps/api`'s Project (and should *not* need to exist on `apps/web`'s Project at all, since per this project's architecture `apps/web` only talks to `apps/api` over HTTP — worth double-checking no code path accidentally imports `libs/database` client-side).

Within a single Project, Vercel further scopes variables by environment — Production, Preview, Development — so the pooled `DATABASE_URL` needs to be explicitly set for the Production environment on `apps/api`'s Project (and a decision made about what, if anything, Preview deployments of `apps/api` should point to — for this project's single-Neon-project scope, pointing Preview at the same pooled string is the simplest option, since there's no Neon branch-per-preview database in play).

**Nx-specific env-var caching trap.** Vercel's own Monorepos FAQ documents a real, named gotcha: *"you may encounter an issue where some of your environment variables are not being assigned the correct value in a specific deployment... the system will look for a value in an existing cache which may or may not be the value you would like to use."* The documented fix is twofold: as a general practice, "define all environment variables in each deployment for all monorepos," and for variables that must bust Nx's computation cache correctly, declare them in `nx.json`: `"namedInputs": { "sharedGlobals": [{ "env": "MY_VERCEL_ENV" }] }` [4]. This is exactly the kind of "worked locally, silently stale in a cached Vercel build" bug that's expensive to debug after the fact — worth wiring proactively for `DATABASE_URL` and any AI-provider API key env vars this project uses, not discovering it after a confusing production incident.

**CORS + Preview deployments.** Because `apps/web` and `apps/api` are separate Vercel Projects, every Preview deployment of `apps/web` gets a brand-new, unpredictable URL (Vercel's `VERCEL_URL` system env var changes on every deployment) [19]. If `apps/api`'s CORS origin is hardcoded to the production `apps/web` domain only, every Preview deployment of `apps/web` will fail CORS calling `apps/api}` in Preview. Two real mitigations exist:
- **Vercel's "Related Projects" feature**: declare `relatedProjects: ["prj_..."]` in `apps/web/vercel.json` (up to 3 related projects, same-repo only), which injects a `VERCEL_RELATED_PROJECTS` env var into the deployment, consumable via the `@vercel/related-projects` npm package's `withRelatedProject()` helper — this wires each Preview of `apps/web` to the matching Preview of `apps/api}` automatically, without hand-maintained URLs [1].
- **A dynamic CORS origin on `apps/api`** rather than a fixed string: NestJS's `enableCors` accepts a function `(origin, callback)` that can validate against an allowlist (env-var-driven, or pattern-matching Vercel's preview URL shape) instead of a single hardcoded origin [search findings, NestJS CORS docs]. Combined with Vercel's `VERCEL_ENV`/`VERCEL_PROJECT_PRODUCTION_URL` system env vars (the latter stays stable across Preview deployments specifically to make this kind of context detection possible) [19], this is a clean way to allow the deployed `apps/web` in both environments without a maintenance burden.

For this project's actual scope (a portfolio/demo app, not a team collaborating on PRs), the pragmatic call is likely: **CORS allows only the fixed production `apps/web` origin**, and Preview-to-Preview cross-testing between the two apps is explicitly out of scope rather than wired up — but this is a real scope decision Story 4.1 should make deliberately, not an oversight to discover later.

### 5. Other current (2026) gotchas for this specific stack

- **Neon free-tier autosuspend (5 min idle) compounds with Vercel cold starts.** A visitor who's the first hit after a quiet period can hit both a Vercel Function cold start *and* a Neon compute wake-up (a few hundred ms) [12][6]. Not a blocker for a portfolio-scale app, but worth setting the generous `connect_timeout` noted above rather than a tight default, and worth setting expectations that "first request after a while" will be visibly slower than steady-state.
- **Migrations need the direct connection string; the running app needs the pooled one** — already covered in depth above, but worth restating as its own operational checklist item, since it's the one place "no application code differs between local and production, only env var values differ" (per this story's own AC) needs a slight refinement: the *migration command's* env var differs in kind (direct vs. pooled), not just in value, from the running app's.
- **Vercel Functions bundle size (250MB default limit)** — worth an early check given LangChain.js's historically large dependency tree; Vercel's own guidance is to keep unused packages in `devDependencies` and audit before assuming this is a non-issue [7][8].
- **Hobby plan = 1 concurrent build.** With two Vercel Projects triggering two deployments per push, a Hobby-tier account serializes them rather than building in parallel — not a correctness issue, just a total-pipeline-time note [4].
- **SSL is required** for any Neon connection; TypeORM's `postgres` driver needs `ssl: true` set explicitly in the DataSource config (Neon's official guide shows this directly) [11].
- **Fluid compute's concurrency-within-one-instance model** means any accidentally-module-scoped mutable state in `apps/api` would be shared across concurrent users, not just concurrent requests from one user [6]. This project's architecture already routes the one stateful concern (rate limiting) through Postgres per AD-2, so this is a validation point rather than new work — worth an explicit "no other module-scoped mutable state" check before Story 4.1 ships.

## Cross-Dimension Insight

Every genuine gotcha found in this research — the Root Directory contradiction (§1), the likely-necessary NestJS build/output override (§2), the Nx env-var cache staleness bug (§4) — is the **same underlying failure mode wearing different clothes**: Vercel's "zero configuration" story for both Nx and NestJS is written and tested against the *simple, single-app, non-monorepo* case, and each of those zero-config assumptions quietly stops being safe to trust the moment Nx's build graph and Vercel's per-framework auto-detection have to cooperate in the same deployment. None of these are hard blockers — every one has a documented, one-line override — but the pattern means Story 4.1 should budget time for "verify the Nx+Vercel combination actually detected things correctly" as its own explicit step for *each* app, rather than assuming that because Next.js-on-Vercel and NestJS-on-Vercel are each individually well-documented as zero-config, deploying both from the same Nx workspace inherits that simplicity for free.

By contrast, the TypeORM/Neon pooling risk (§3) — the one the architecture review specifically flagged as a concern — turned out to be **the one area where the defaults are actually already correct**. The risk is real in the ecosystem (Prisma's multi-year PgBouncer saga is genuine and well-documented) but doesn't transfer to TypeORM's default query path, because the two ORMs make different default choices about *named* vs. *unnamed* prepared statements at the driver level. The only real action item this produces is operational (a second, direct connection string for migrations only) rather than a runtime code change.

## Contrary Evidence

The strongest case against "TypeORM is fine by default" would be a documented TypeORM+PgBouncer prepared-statement failure report. None was found: the `typeorm/typeorm` issue tracker search for "pgbouncer" returned 3 results, all unrelated to prepared statements [17]. This is reasonably strong negative evidence given how prominent and long-running the equivalent Prisma issue threads are [16] — if TypeORM had the same default behavior, a similarly-aged and similarly-active issue tracker would very likely show it. The caveat: absence of GitHub issues isn't a formal guarantee, and this project's exact query patterns (via `libs/retrieval`'s vector-search queries, which may include pgvector-specific operators) haven't been tested against Neon's pooler in this research — this should be confirmed empirically once ingestion + the first real API queries run in Story 4.1, not assumed purely from this research.

## Recommendations

1. **Deploy `apps/web` and `apps/api` as two separate Vercel Projects against the same repo.** Follow Nx's Root-Directory guidance (leave it at the repo root, override Build Command to `npx nx build <app>` and Output Directory to the actual Nx build output) rather than the generic monorepo "set Root Directory to the app subfolder" flow. *(Feeds: Story 4.1 setup steps.)*
2. **Treat the Nx+NestJS combination as unverified until deployed once.** Deploy a minimal `apps/api` first and confirm Vercel actually finds/builds the NestJS entrypoint through Nx's build output before wiring up the full app. *(Feeds: Story 4.1, first implementation step — de-risks the single biggest unknown in this research.)*
3. **Do not add any TypeORM statement-caching workaround, and do not adopt `@neondatabase/serverless`.** TypeORM's default unnamed-statement behavior via `pg` is already safe against Neon's pooled/PgBouncer-transaction-mode endpoint. *(Feeds: `apps/api`'s DataSource config — no change needed beyond what's below.)*
4. **Provision two connection strings, not one:** `DATABASE_URL` (pooled, `-pooler` host, used by the running app and by ingestion) and a direct (non-pooled) URL used only by the migration command. Add `ssl: true` and a generous `connect_timeout` (e.g. `10`) to the pooled string. *(Feeds: `apps/api` env var setup, migration tooling config.)*
5. **Set `extra.max` on the TypeORM DataSource to a modest, deliberate number** rather than leaving `pg`'s default, given PgBouncer is already doing the real pooling. *(Feeds: DataSource config.)*
6. **Set `DATABASE_URL` (and any other secret) independently on `apps/api`'s Vercel Project**, and add the relevant env vars to `nx.json`'s `namedInputs.sharedGlobals` to avoid Nx's build-cache staleness bug. *(Feeds: Vercel Project setup for both apps.)*
7. **Decide CORS scope deliberately**: fixed production origin only (simplest, matches a portfolio-scale project) vs. wiring Vercel's Related Projects + a dynamic CORS origin function for Preview-to-Preview testing. Either is defensible; picking implicitly by not thinking about it is the failure mode to avoid. *(Feeds: `apps/api`'s `main.ts` CORS setup, `AD-1`.)*
8. **Audit `apps/api` for module-scoped mutable state** before go-live, given Fluid compute serves concurrent requests from the same warm instance. This project's rate-limit design (Postgres-backed, AD-2) already gets this right — the audit is a confirmation, not expected new work. *(Feeds: pre-launch checklist.)*
