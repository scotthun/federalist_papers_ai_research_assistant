- (decision) AD: Deployment target is Vercel for both apps (Next.js web + NestJS api, api deployed via Vercel's native zero-config NestJS serverless support) plus Neon for Postgres+pgvector. Binds: hosting model. Prevents: assuming a single always-on process is available in production.
- (decision) AD: The daily rate-limit cap counter lives as a row in Postgres (atomic UPDATE/UPSERT), not in-memory and not Redis. Binds: rate-limiter implementation. Prevents: the counter silently resetting on every serverless cold start, which would happen if it were in-memory.
- (constraint) NestJS must connect to Neon via its pooled connection string in production, never the direct connection string, to avoid exhausting Postgres connection limits under serverless concurrency (documented gotcha: each cold invocation can open a fresh DB connection).
- (decision) AD: Local development uses Docker Compose for exactly one thing -- a pgvector/pgvector Postgres container. NestJS (nest start) and Next.js (next dev) run as normal local processes, not containerized. Docker Compose is never part of the production deployment artifact -- Vercel builds/deploys directly from source. Binds: local dev setup. Prevents: docker-compose being mistaken for or reimplemented as a deployment mechanism.
- (decision) AD: Environment differences (which Postgres, which API keys) are expressed exclusively through environment variables (DATABASE_URL, provider API key, etc.), never through environment-conditional code branches (no 'if isProd' logic for connection setup). Binds: all environment-dependent configuration. Prevents: local-only hardcoded values or divergent code paths per environment.
- (note) Ingestion (npm run ingest:federalist-papers) is a manual/occasional operational script, run by hand against whichever DATABASE_URL is active -- not part of the automatic Vercel deploy pipeline. Run once against local Docker Postgres during development, once against Neon before/after the first production deploy, and again only on a source pivot per the SOURCE DECISION re-ingestion strategy.

- (decision) AD: libs/database, libs/ai, libs/documents are sibling leaf libs with zero cross-dependencies on each other -- each owns exactly one concern (Postgres/pgvector schema+repos; AI provider abstraction, domain-agnostic; parsing/chunking). Binds: lib boundaries. Prevents: any leaf lib reaching into another's domain.
- (decision) AD: libs/retrieval depends on libs/database (pgvector query) and libs/ai (query embedding), and returns only chunks -- it has no knowledge of confidence thresholds or citations. Binds: retrieval's responsibility boundary. Prevents: confidence/citation logic leaking into the retrieval layer.
- (decision) AD: The orchestrating service (confidence-threshold check, prompt construction, citation verification, structured-response assembly) lives directly in apps/api, depending on libs/retrieval + libs/ai -- NOT promoted to a new libs/rag or libs/qa, per Rule of Three (apps/web only calls api over HTTP; the eval script needs raw retrieval only). Binds: where orchestration logic lives. Prevents: a premature shared-lib abstraction with only one real consumer. Validated against Nx's own feature/data-access/util lib categorization and two real open-source NestJS RAG repos (Sama-ndari/enterprise-rag-chatbot, ErfanSeidipoor/nestjs-langgraph-pgvector-rag), both of which independently keep threshold/citation logic out of their retrieval and LLM-provider modules for the same mechanical reason: only the orchestrator holds both the retrieved chunks and the LLM output at once.
